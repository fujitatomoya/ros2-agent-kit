# API and ABI stability

Released distributions receive patch releases that must be binary compatible.
`rolling` may change API across a release boundary, with a deprecation cycle.

## What breaks ABI in C++

- Adding, removing, or reordering data members of a class that users construct or subclass.
- Adding, removing, or reordering virtual functions, or changing their signatures.
- Changing a function's signature, including `const`, parameter types, or return type.
- Changing an inline function or template whose body users compiled in, when behavior changes.
- Changing enum values or the underlying type.
- Changing a default argument value; the old value is compiled into callers.
- Changing exception specifications or `noexcept`.

Safe on a released distribution: adding a non-virtual member function, adding a free function, adding a new class, adding an enumerator at the end when the enum is not used in switch statements that must be exhaustive, and changes inside a `.cpp` that keep observable behavior.

PIMPL classes (`std::unique_ptr<Impl> impl_`) and `rcl` structs with explicit `_zero_initialized` and size fields exist to make growth possible; use them for anything expected to evolve.

## Deprecation (tick-tock)

1. Tick: add the replacement, mark the old API `[[deprecated("use foo() instead")]]`, keep it working, document the change.
   Guard the attribute with the package's macro when one exists, for example `RCLCPP_DEPRECATED`.
2. Tock: remove it in the next ROS distribution, never in a patch release.

No new deprecation on a released distribution; a backport must not add one.

## Visibility

Every exported symbol in a shared library uses the package's visibility macro (`RCLCPP_PUBLIC`, `RCL_PUBLIC`), generated by `visibility_control.h`.
A missing macro is an ABI change by omission on Windows.

## Checking

```bash
# dump before and after, then compare
abi-dumper libfoo.so -o before.dump -lver 1
abi-dumper libfoo.so -o after.dump -lver 2
abi-compliance-checker -l foo -old before.dump -new after.dump
```

`ros2/ci` offers an ABI check job; ask a maintainer to run it through `ci-trigger` with the ABI option when the change touches a public header on a released distribution.
Describe the result in the PR packet under "Verification performed".

## RMW API

A change to the `rmw` API requires updating the tier 1 RMW implementations (`rmw_fastrtps`, `rmw_cyclonedds`, `rmw_connextdds`) in the same change set, and usually `rcl` and `rclcpp`.
Bundle those PRs in one `ci-trigger` run with `--pulls`.
